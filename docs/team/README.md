## 开发顺序

1. 各自拉取最新main，跑通已有版本。A优先在R9000P确认Java、Node、Git与MySQL环境。
2. A先交付最小组织、员工、场所模型与共享接口；B并行开发规则/工时计算逻辑；C并行开发文件解析与知识检索逻辑。未接业务数据的页面显示空状态。
3. A的基础模型合并后，B接打卡，A继续审批，C继续知识问答；B公布考勤查询和审批调整服务后，A接回写、C接报表和AI考勤查询。
4. 各自完成后共同联调“建档→打卡→申请/审批→报表→AI查询”，按实际结果更新整体进度。

详细字段、文件边界与迁移顺序见 [公共约定](contracts.md)。

## GitHub同步规则

开发前获取最新main并检查本机未提交修改，保留用户改动。每完成一小阶段，运行相关检查、commit、push个人分支、创建或更新PR；合并前同步main、解决冲突并核对迁移。一个PR合并后，下一阶段使用新的分支。

本机保存和commit不等于上传成功。交付时必须确认远端已收到提交，提供分支、SHA、PR、测试结果和未完成项；推送失败保留本机成果并报告原因。不用force push覆盖他人提交，不自动清空用户改动或数据库。

B、C需要先获得私有仓库协作者权限，并在各自电脑登录GitHub。三个Codex对话不自动共享聊天记录，以仓库文档和最新代码为共同依据。仓库保持私有，公有化由持有人另行操作。
