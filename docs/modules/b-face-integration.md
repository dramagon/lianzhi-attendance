## 获得SDK后的实现顺序

1. 在目标设备独立验证官方示例：原生库加载、授权、版本读取、检测、特征提取、比对、活体分别运行，记录错误码与环境，不记录真实人脸。
2. 扩展现有FaceProvider适配层，将官方SDK生命周期、线程模型和资源释放放在适配器内部。能力状态来自实际初始化结果；依赖缺失、授权失效、引擎失败时关闭相应功能。
3. 评审并启用V5：登记元数据、特征版本、验证挑战与审计按需建模。特征加密存储，密钥独立配置；照片默认不留存。更新/删除撤销旧版本及未消费验证凭据，用户身份沿用sys_user.id。
4. 登记、更新、删除和采集说明连接真实本人身份；后端校验图像大小/格式、人数、质量及活体。管理员处理他人登记需单独定义并审计授权范围，不复用头像做特征。
5. 服务端创建短时、一次性挑战，绑定当前员工、场所和打卡请求。后端调用实际检测/比对/活体，不接受前端布尔成功值。验证通过只生成服务端可信凭据，最终打卡仍复核排班、范围、定位、时间和防重。
6. 人脸必需场所只在上述链路真实可用时开放；失败、过期、撤销授权、网络中断均不得绕过人脸要求。原始考勤事件继续不可改写。

## 必须保留的验收证据

- 分别记录检测、比对、活体结果与真实SDK版本，不把三者合并成一个“已完成”。
- 本人登记→更新→旧特征失效→删除→不能继续验证；覆盖未登记、多人、图像损坏、低质量及比对失败。
- 错误员工、场所、挑战或请求的凭据拒绝；过期、重放和并发消费拒绝；前端伪造成功不产生打卡事件。
- 授权失效、原生库缺失、引擎异常和断网显示明确状态；真实手机上的允许、拒绝、切后台与恢复单独记录。
- Windows/Linux、具体手机和实际SDK只勾选确实运行过的组合，不用云端浏览器仿真代替。

## 已有业务与启用条件

- FaceProvider为服务端可信适配接口：capabilities必须来自真实SDK初始化与授权；analyze必须执行真实单人检测、质量、活体及特征提取；compare返回实际比对的归一化分数。没有实际适配器时不注册任何默认成功实现。适配器必须返回本次调用独立拥有的特征字节，业务层使用后清零，不能返回共享SDK缓冲区。
- 全部条件同时具备才允许采集：enabled=true、恰好一个真实适配器且三项能力可用、V4/V5已正式成功迁移、32字节Base64加密密钥有效、实际校准阈值位于(0,1)。仅设置开关不能绕过缺失依赖。
- V5候选在`docs/modules/b-pending-migrations/V5__face.sql`，不在默认Flyway目录。不能单独手动建表骗过状态；服务还检查正式V4/V5成功历史。测试只在自己的隔离数据库应用A/B候选SQL。
- 配置名见[b-face-config.env.example](b-face-config.env.example)。密钥需安全保存且重启稳定，应用不自动生成或输出；改变密钥会使旧特征不可解密。当前无在线密钥轮换工具，轮换前需受控迁移或明确删除并重新登记，不能仅替换环境变量。
- `LIANZHI_FACE_REQUIRED=true`对所有打卡强制要求服务端凭据，即使SDK不可用也不会退回二维码成功。默认false以保留现有二维码打卡；按场所的faceRequired适配字段同样进入服务端校验。A的场所档案当前未提供独立人脸策略字段，不伪造为已实现逐场所配置。
- 图像不作业务持久化或日志记录，控制器处理后清零自己的字节数组；Servlet multipart可能使用请求期临时缓存，并不承诺所有传输缓冲都只在内存。部署时为临时上传目录设置受控权限、清理与磁盘保护，禁止代理记录请求体；不把SDK/原生库的内部内存释放视为Java数组清零已经覆盖。
- SDK/密钥不可用时本人仍可删除已登记特征和未消费挑战（需正式存储存在）；删除不修改原始考勤，审计只保留用户ID、操作、版本和时间。

## 验证范围

FaceWorkflowTest使用明确的TEST_ONLY_SIMULATOR，验证加密、版本、所有权、活体/比对失败、三次尝试、第三次成功、过期、重放、并发消费、回滚和HTTP的CSRF/本人范围。它证明业务安全流程，不证明实际识别准确率、真实活体或Windows原生库运行。
