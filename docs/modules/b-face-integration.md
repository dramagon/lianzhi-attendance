# B真实人脸接入交接

更新：2026-11-08。已新增可选 ArcFace Java Windows x64 V3.0 适配器，本机授权激活、初始化及真实SDK无脸拒绝通过。本人/非本人比对、真实摄像头RGB活体、阈值校准与完整打卡现场验收仍未通过；不能将初始化成功当作这些项目已验收。以下旧交接描述保留历史背景，以本节最新结果为准。

## 2026-11-08 本机接入

`ArcSoftFaceProvider` 可选加载本机官方 `arcsoft-sdk-face-3.0.0.0.jar` 和三个 WIN64 DLL，不把授权SDK或密钥打包。默认不开启，未配置机器仍按原流程关闭采集。实际引擎版本 `3.0.3902010101.5`，使用IMAGE模式、RGB活体、特征提取和比较；没有接入IR硬件或IR活体。采用单引擎串行调用及退出释放，反射/原生调用异常或SDK内部错误关闭引擎，不返回成功样本。损坏输入及无脸、多人、姿态/曝光不合格、活体非1均不能生成可用特征。

服务端对图片尺寸/编码先检查，再经SDK转换、检测；人脸区域至少80×80、完整位于图内，灰度均值25～230及标准差至少12，姿态三轴不超过20度。这些是应用预检查，不是虹软质量分数或经过人群验证的准确率标准。实际SDK的低置信度提取结果也作为拒绝处理。RGB活体运行阈值通过 `LIANZHI_ARCSOFT_RGB_LIVENESS_THRESHOLD` 显式配置（默认0.8）；它不是身份比对阈值，现场仍须测试照片、屏幕与实际摄像头。

`start-ai.cmd` 通过PowerShell入口读取忽略目录 `artifacts/arcsoft-credentials.local.ps1`，将授权、SDK路径传给实际Java应用；已有AI/OCR/转写和原本机资料保留。特征加密密钥由本机配置工具一次性生成后明确保存，应用自身不生成临时密钥。该文件和SDK的 `ArcFace*.dat` 设备激活缓存均不入Git。

`LIANZHI_FACE_MINIMUM_SCORE` 仍无猜测默认值。必须完成目标摄像头上的本人/非本人试验后，在本机明确配置身份阈值；否则status提示未校准、available=false，采集/登记/验证保持关闭。不得为了展示而绕过此门槛或开启人脸必需策略。本人图像只通过主动同意的采集流程处理，不能从账号头像自动登记。

本机证据见 [A虹软接入记录](../verification/member-a-arcsoft-2026-11-08.md)。现有HTTP接口、Session/CSRF、特征加密、挑战、版本与一次性打卡消费契约保持不变。SDK属性见 `b-face-config.env.example`。

已实现SDK之外的业务流程：本人登记、乐观版本更新、删除、AES-256-GCM特征加密、一次性挑战、服务端结果判定与打卡同事务消费，以及手机采集界面。SDK处理默认关闭；2026-11-03已接入A正式V4/V4.1并发布V5存储；2026-11-08新增上述真实适配器。测试中的SDK替身仅在src/test中，不打包到运行JAR。

用户已提供Windows x64 V3.0 SDK和对应授权，A本机激活与引擎初始化通过；云端Linux没有对应运行库或授权，不宣称云端通过。官方账号、下载及设备授权由具有对应账号/许可的人员办理，不能用项目测试替身替代。

## 获得SDK后的实现顺序

1. 在目标设备独立验证官方示例：原生库加载、授权、版本读取、检测、特征提取、比对、活体分别运行，记录错误码与环境，不记录真实人脸。
2. 扩展现有FaceProvider适配层，将官方SDK生命周期、线程模型和资源释放放在适配器内部。能力状态来自实际初始化结果；依赖缺失、授权失效、引擎失败时关闭相应功能。
3. V5存储已发布，登记元数据、特征版本、验证挑战与审计已有实现。特征加密存储，密钥独立配置；照片默认不留存。更新/删除撤销旧版本及未消费验证凭据，用户身份沿用sys_user.id。
4. 登记、更新、删除和采集说明连接真实本人身份；后端校验图像大小/格式、人数、质量及活体。管理员处理他人登记需单独定义并审计授权范围，不复用头像做特征。
5. 服务端创建短时、一次性挑战，绑定当前员工、场所和打卡请求。后端调用实际检测/比对/活体，不接受前端布尔成功值。验证通过只生成服务端可信凭据，最终打卡仍复核排班、范围、定位、时间和防重。
6. 人脸必需场所只在上述链路真实可用时开放；失败、过期、撤销授权、网络中断均不得绕过人脸要求。原始考勤事件继续不可改写。

## 必须保留的验收证据

- 分别记录检测、比对、活体结果与真实SDK版本，不把三者合并成一个“已完成”。
- 本人登记→更新→旧特征失效→删除→不能继续验证；覆盖未登记、多人、图像损坏、低质量及比对失败。
- 错误员工、场所、挑战或请求的凭据拒绝；过期、重放和并发消费拒绝；前端伪造成功不产生打卡事件。
- 授权失效、原生库缺失、引擎异常和断网显示明确状态；真实手机上的允许、拒绝、切后台与恢复单独记录。
- Windows/Linux、具体手机和实际SDK只勾选确实运行过的组合，不用云端浏览器仿真代替。

## 已有业务与启用条件

- FaceProvider为服务端可信适配接口：capabilities必须来自真实SDK初始化与授权；analyze必须执行真实单人检测、质量、活体及特征提取；compare返回实际比对的归一化分数。没有实际适配器时不注册任何默认成功实现。适配器必须返回本次调用独立拥有的特征字节，业务层使用后清零，不能返回共享SDK缓冲区。
- 全部条件同时具备才允许采集：enabled=true、恰好一个真实适配器且三项能力可用、V4/V4.1/V5已正式成功迁移、32字节Base64加密密钥有效、实际校准阈值位于(0,1)。仅设置开关不能绕过缺失依赖。
- V5已位于`backend/src/main/resources/db/migration/V5__face.sql`，默认随V4、V4.1之后迁移。存储与SDK处理分开启用：建表不会采集特征，不需SDK授权；图像处理仍受所有配置门槛限制。服务检查三项成功历史，不手动造表或伪造Flyway历史。此前候选仅用于测试，已移除；已正式发布的迁移不能改写。
- 配置名见[b-face-config.env.example](b-face-config.env.example)。密钥需安全保存且重启稳定，应用不自动生成或输出；改变密钥会使旧特征不可解密。当前无在线密钥轮换工具，轮换前需受控迁移或明确删除并重新登记，不能仅替换环境变量。
- `LIANZHI_FACE_REQUIRED=true`对所有打卡强制要求服务端凭据，即使SDK不可用也不会退回二维码成功。默认false以保留现有二维码打卡；按场所的faceRequired适配字段同样进入服务端校验。A的场所档案当前未提供独立人脸策略字段，不伪造为已实现逐场所配置。
- 图像不作业务持久化或日志记录，控制器处理后清零自己的字节数组；Servlet multipart可能使用请求期临时缓存，并不承诺所有传输缓冲都只在内存。部署时为临时上传目录设置受控权限、清理与磁盘保护，禁止代理记录请求体；不把SDK/原生库的内部内存释放视为Java数组清零已经覆盖。
- SDK/密钥不可用时本人仍可删除已登记特征和未消费挑战（需正式存储存在）；删除不修改原始考勤，审计只保留用户ID、操作、版本和时间。

## 验证范围

FaceWorkflowTest使用明确的TEST_ONLY_SIMULATOR，验证加密、版本、所有权、活体/比对失败、三次尝试、第三次成功、过期、重放、并发消费、回滚和HTTP的CSRF/本人范围。它证明业务安全流程，不证明实际识别准确率、真实活体或Windows原生库运行。
